# Ручное добавление и сопряжение одного ТВ

Дата: 2026-10-03.
Статус: утверждено владельцем 2026-10-03; основа плана реализации.

Основа: [ТЗ MVP](2026-09-02-remote-webos-tv-mvp-design.md), разделы 7–8 и 10–11. Этот документ уточняет первый вертикальный шаг этапа 2, а не заменяет требования полного MVP.

## Цель и границы

Авторизованный владелец добавляет один LG webOS TV вручную, подтверждает запрос на экране ТВ и получает сохранённую настройку. При повторном открытии приложения или перезапуске backend виден тот же телевизор; сохранённый ключ используется без нового запроса подтверждения.

Включены: ввод IP, сопряжение, отмена и тайм-аут, зашифрованное хранение ключа, модель и статус ТВ, восстановление подключения, изменение адреса и явное повторное сопряжение после отзыва доступа.

Не включены: discovery, пульт и команды управления, Wake-on-LAN из браузера, несколько ТВ, видео, реалистичный дизайн, Docker и сервисное размещение. Никаких неработающих кнопок будущего пульта.

## Пользовательский путь

1. Без действующей сессии пользователь видит вход. С действующей сессией сразу открывается главный экран.
2. Если сохранённого ТВ нет, отображается форма «IP-адрес телевизора» и кнопка «Подключить». Рядом указано: ТВ должен быть включён и доступен серверу; управление мобильными устройствами должно быть разрешено.
3. После запуска отображаются инструкция подтвердить доступ на ТВ, отсчёт оставшегося времени и «Отменить». Общий бюджет операции — 60 секунд с момента принятия backend, включая подключение и проверку результата; обновление страницы его не продлевает.
4. После подтверждения backend проверяет регистрацию, сведения о модели и безопасное чтение состояния. Только после успешного сохранения UI показывает настроенный ТВ и статус «Подключён».
5. При отказе, тайм-ауте или отмене показывается конкретная безопасная причина и возможность явного повтора. Неуспешная первая операция не создаёт сохранённый ТВ.
6. Обновление или закрытие страницы не отменяет серверную операцию. Повторно открытая страница показывает текущую операцию и её оставшееся время. Отмена выполняется только отдельным защищённым запросом; остановка backend также отменяет работу.

## Повторный вход и сохранённый ТВ

- Настройка хранится в постоянном каталоге данных, не в браузере. Выход из аккаунта не удаляет ТВ и не отключает серверное соединение.
- При запуске backend загружает сохранённую настройку и подключается с сохранённым ключом. Открытие страницы не создаёт новое соединение на каждую вкладку.
- UI сразу показывает сохранённую модель и IP, отдельно от текущего статуса. Во время подключения — «Подключение», при выключенном или недоступном ТВ — «Нет соединения»; настройка сохраняется.
- Недоступность не означает ошибку авторизации. Отозванный ключ даёт отдельный статус и действие «Повторить сопряжение»; автоматическое переподключение не запускает новый PROMPT.
- Изменение IP не создаёт второй ТВ: backend сначала проверяет новый адрес с существующим ключом и сохраняет его только после успеха. При неудаче предыдущая настройка остаётся. Совпадение модели само по себе не доказывает идентичность устройства.
- Для восстановления после недоступности есть «Подключиться снова». На этом шаге выполняется автоматическая попытка при старте и ограниченная попытка по явному действию; фоновый backoff и push-события полного Connection Manager остаются следующим шагом. UI не обещает мгновенного автоматического обнаружения включённого ТВ.

## Архитектура и владельцы данных

Браузер → защищённый Fastify API → TV Service → существующий webOS Adapter → ТВ. Протокольные детали и транспорт остаются в adapter; браузер не соединяется с ТВ напрямую.

- SQLite — источник истины для единственной настройки: адрес, проверенная модель/сведения об устройстве и зашифрованный client-key. Runtime-статус соединения не выдаётся за постоянное состояние.
- Адрес и ключ сохраняются одной транзакцией, после успешной регистрации и проверки. В случае сбоя записи операция завершается ошибкой, а предыдущее состояние остаётся целым.
- Криптография переиспользует существующий механизм AES-256-GCM, не вводит второй независимый алгоритм. Отдельный файловый мастер-ключ остаётся вне SQLite, с минимальными правами доступа. Его потеря при наличии шифротекста — явная ошибка, а не повод создать новый ключ поверх старого.
- CLI/protocol probe продолжает использовать своё файловое хранилище. Автоматического переноса ключа, адреса или данных стенда нет.
- Adapter сейчас сохраняет ключ через `ClientKeyStore` ещё до завершения `pair`. Для веб-операции этот интерфейс получает изолированное временное хранилище в памяти: запись adapter не равна фиксации настройки. TV Service коммитит результат только после проверки и подтверждения, что операция ещё актуальна. Поведение CLI не меняется.
- TV Service владеет одним активным adapter, отменой и завершением операций. Shutdown закрывает соединения до закрытия SQLite. Ошибка очистки наблюдаема и не подменяет исходную причину.

## Операции, состояния и конкурентность

Используются существующие состояния `unconfigured`, `pairing`, `connecting`, `available`, `unavailable`, `authorization_error`, `compatibility_error`. Фоновое `reconnecting` станет активно при реализации backoff; новые дублирующие состояния не вводятся.

Каждая изменяющая операция имеет серверный идентификатор. Одновременно разрешена одна операция настройки/сопряжения/изменения адреса/подключения; конкурентный запуск получает явный конфликт и не вытесняет текущую операцию.

Отмена относится к конкретному идентификатору, повторная отмена не запускает новую работу. Поздний результат отменённой или истёкшей операции не меняет SQLite и текущий runtime-статус. Если фиксация уже завершилась, отмена сообщает, что операция завершена, и не удаляет сохранённый ТВ.

При повторном сопряжении и изменении адреса старую настройку не удаляют до успешной замены. При прерывании процесса незавершённая операция не возобновляется как новое сопряжение; сохранённый ТВ восстанавливается, несохранённый остаётся `unconfigured`.

Доступность подтверждается безопасным чтением через adapter. В ходе отображения состояния backend проверяет соединение ограниченным чтением с единым in-flight запросом для всех вкладок; GET не запускает сопряжение и не меняет постоянную настройку. Если проверка связи неуспешна, статус перестаёт быть `available`.

## Защита и API

- Чтение модели, IP, статуса и операций доступно только авторизованному владельцу. Существующие Origin/CSRF, `no-store` и безопасные HTTP-ошибки сохраняются.
- Запуск сопряжения и повторные попытки ограничены: не более 5 принятых попыток за 60 секунд на владельца; превышение — 429 с Retry-After. Конфликт активной операции не создаёт ещё одну сетевую попытку.
- Форма принимает только буквальный IPv4-адрес локальной частной сети RFC1918. URL, hostname, пользовательский порт, loopback, unspecified, multicast и broadcast запрещены. IPv6 и расширение диапазонов остаются отдельным улучшением; это явное ограничение первого шага, не всего MVP.
- Adapter использует только существующие протокольные порты 3001/3000 и secure-first поведение. Разрешённый владелец не получает универсальный HTTP/WebSocket-прокси к произвольным адресам.
- Обычные логи не содержат IP/MAC, ключа, raw payload, cookie, токенов или внутренних путей. IP показывается только в защищённом UI как настройка владельца.
- Браузер получает только публичную проекцию настройки и безопасный результат операции; client-key, шифротекст и мастер-ключ не выдаются даже авторизованному пользователю.
- UI получает статус через защищённые REST-чтения, без WebSocket в этом шаге. Опрос не чаще раза в 2 секунды, без перекрытия запросов; прекращается при logout/размонтировании, возобновляется с полным снимком. Серверный срок операции — источник истины для таймера.

## Ошибки и критерии приёмки

Отдельно различаются неверный адрес, конфликт, ограничение попыток, недоступность сети, отказ, тайм-аут, отмена, невалидный ключ, несовместимый ответ, ошибка шифрования/хранилища. Используются нормализованные ошибки adapter; UI не показывает raw исключения.

Приёмка требует свежих подтверждений:

1. Mock-TV: успешный путь, отказ, тайм-аут, отмена, разрыв на разных границах; ключ не сохраняется при неуспехе.
2. Детерминированные гонки: двойной запуск, отмена во время регистрации/сохранения, поздний результат; один активный процесс и отсутствие записи после принятой отмены.
3. SQLite: миграция существующей установки, атомарность настройки, зашифрованный ключ, ошибочная запись, повреждённый/отсутствующий мастер-ключ. Владелец и сессии не теряются.
4. API: отсутствие авторизации, Origin/CSRF, валидация адреса, rate limit и отсутствие секретов в JSON/логах.
5. Chromium: вход → форма → сопряжение → сохранённый ТВ; обновление во время операции; выход/повторный вход; рестарт backend; выключенный ТВ; изменение адреса и отзыв доступа.
6. Реальный ТВ: пользователь подтверждает PROMPT; UI показывает проверенную модель; после перезапуска backend и повторного входа ТВ остаётся и подключается без нового PROMPT. Выключенный ТВ остаётся сохранённым. Фактические аппаратные действия выполняются по согласованию с пользователем.

Результаты mock-тестов не заменяют аппаратный прогон. Успех этого этапа не объявляет готовыми пульт, discovery, Docker или полный MVP.
