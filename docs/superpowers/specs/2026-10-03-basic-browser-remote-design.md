# Базовый пульт в браузере — следующий вертикальный шаг

**Дата:** 2026-10-03
**Статус:** согласован состав; письменная спецификация ожидает подтверждения владельца.
**Основа:** [ТЗ MVP](2026-09-02-remote-webos-tv-mvp-design.md), [дорожная карта](../plans/2026-09-02-remote-webos-tv-mvp-roadmap.md).

## 1. Цель и исходное состояние

Владелец управляет уже сохранённым телевизором из браузера компьютера. При повторном входе не нужно заново сопрягать ТВ. Главное — работающие команды и понятные ошибки, а не внешний вид физического пульта.

Основа приложения и ручное сопряжение слиты в `main` через PR #2 и #3. Существующий `WebOsAdapter` уже предоставляет `sendButton`; базовый TV Service управляет сохранённой настройкой и соединением, но ещё не предоставляет команды браузеру. Новый шаг расширяет эти границы, не создаёт второй adapter или отдельное соединение на каждое нажатие.

## 2. Состав шага

- Десять команд: `UP`, `DOWN`, `LEFT`, `RIGHT`, `ENTER`, `BACK`, `HOME`, `VOLUME_UP`, `VOLUME_DOWN`, `MUTE`.
- Простые подписанные кнопки, навигационный блок, громкость и отключение звука.
- Однократные нажатия мышью и клавиатурой.
- Защищённый REST API, проверка соединения и возможности pointer, ограничение частоты.
- Явное различение отправки, отказа до отправки и неизвестного результата.
- Детерминированные автоматические проверки и отдельная ручная приёмка на ТВ.

Удержание, питание/WOL, каналы, цифры, меню/Exit, приложения, входы, текст, уведомления, WebSocket API, discovery и фоновый reconnect не входят в этот шаг. Удержание остаётся требованием полного MVP, а не отменяется этим срезом. Передача изображения и реалистичный дизайн пульта по-прежнему вне MVP.

## 3. Выбранный подход

Делаем сквозной минимальный путь UI → Backend API → TV Service → существующий webOS Adapter. API-only отложил бы проверку владельцем, а весь пульт сразу увеличил бы объём аппаратных проверок и риски.

Общие строгие схемы команд и результатов принадлежат `packages/contracts`. Авторизация и HTTP принадлежат API, жизненный цикл и допуск команды — TV Service, SSAP/pointer и классификация транспортных ошибок — adapter. UI не получает ключ сопряжения и не обращается к ТВ напрямую.

Существующие маршруты сопряжения и их ответы сохраняются. Миграция базы для этого шага не требуется. Возможности ТВ для пульта предоставляются отдельным защищённым представлением либо совместимым расширением статуса; окончательная схема фиксируется в плане реализации до кода. Отсутствие подтверждённой возможности не разрешает отправку.

## 4. Поток команды и конкуренция

1. На одно пользовательское нажатие UI создаёт уникальный идентификатор и отправляет одну команду из закрытого списка.
2. API проверяет сессию, Origin, CSRF, строгую схему и частоту до вызова adapter. Ответы имеют `Cache-Control: no-store`.
3. TV Service допускает команду только при `available`, поддерживаемом pointer и отсутствии несовместимой операции жизненного цикла.
4. Используется текущий adapter. Не выполняются сопряжение, переключение адреса или автоматическое переподключение ради команды.
5. Ответ содержит исходный идентификатор и безопасный нормализованный результат.

Одна команда исполняется за раз на телевизор, включая запросы из разных вкладок. Следующая параллельная команда получает явный отказ «занято», не ставится в очередь. Пока нажатие выполняется, UI временно отключает командные кнопки. Pair/reconnect/change address/repair и команды не должны использовать или закрывать один adapter одновременно: TV Service владеет общим допуском. Проверка статуса не должна приводить к поздней отправке команды после смены поколения соединения.

Ограничение команды — общий бюджет 5 секунд на подготовку pointer и отправку, измеряемый монотонными часами. Timeout, logout, закрытие сервиса и замена соединения прекращают ещё не отправленную работу; после отправки не обещается откат действия. Backend ограничивает владельца десятью принятыми командами в секунду. Время и лимиты тестируются через управляемые зависимости, без ожиданий реального времени.

Идентификатор служит корреляции, а не обещанию постоянной идемпотентности. UI и API не повторяют запрос автоматически ни после timeout, ни после потери HTTP-ответа; новый явный клик — новая команда. Этот шаг не предоставляет гарантии exactly-once для произвольных клиентов, повторно отправляющих HTTP-запросы.

## 5. Семантика результата

Pointer-команда не даёт подтверждения изменения изображения на ТВ. Завершение `sendButton` означает только успешное выполнение предусмотренного adapter пути отправки, а не доказательство эффекта на экране.

- **Отправлено:** «Команда отправлена». Не показываем «Телевизор выполнил команду».
- **Отказ до отправки:** недоступность, занятость, неподдерживаемая возможность, неверный запрос или лимит. Пользователь видит конкретную безопасную причину.
- **Результат неизвестен:** разрыв или timeout, когда отправка уже могла произойти, либо потеря HTTP-ответа. UI предупреждает: «Результат команды неизвестен. Автоматический повтор не выполняется».

Неопределённость устанавливается на границе, где известна стадия отправки; потребители не угадывают её по тексту исключения. Неподдерживаемая возможность отключается с объяснением. Проблема pointer не должна без доказательства превращать всё SSAP-соединение в недоступное. Диагностика не содержит ключей, адреса ТВ, cookie или пароля.

Выключенный/отключённый ТВ остаётся сохранённым. Команды блокируются с объяснением, путь явного reconnect остаётся доступен. После восстановления не отправляется ни одна старая команда.

## 6. Клавиатура и браузерный жизненный цикл

На сфокусированном блоке пульта: стрелки — навигация, Enter — OK, Escape — Back, Home — Home, `+`/`-` — громкость, `M` — mute. Подсказки видимы в UI. При фокусе в поле ввода, вне блока пульта или при Ctrl/Alt/Meta сочетания не перехватываются.

События `KeyboardEvent.repeat` игнорируются: удержание не создаёт последовательность команд. Нативная активация кнопок и общий обработчик клавиатуры не должны отправлять одну команду дважды. После logout, потери сессии или размонтирования поздний ответ не восстанавливает старый экран и не изменяет новую сессию. Потеря фокуса/видимости не порождает новых команд; уже отправленное действие не считается отменённым.

## 7. Проверки и критерии приёмки

- Строгие схемы принимают только согласованные кнопки и отклоняют неизвестные поля/значения.
- Неавторизованный запрос, неверный Origin/CSRF и превышение лимита не вызывают adapter.
- Mock-TV подтверждает путь каждой кнопки через реальный adapter, а не только вызов заглушки сервиса.
- Детерминированно проверяются offline, отсутствие pointer, конкуренция вкладок, конфликт с lifecycle-операцией, timeout и разрыв до/после возможной отправки. Поздняя работа не попадает на новое соединение; автоматических повторов и очереди нет.
- Chromium проверяет мышь, клавиатуру, отсутствие двойного нажатия/repeat, фокус полей, блокировку offline, неизвестный результат, logout и повторный вход с сохранённым ТВ.
- На физическом ТВ владелец отдельно подтверждает видимый эффект навигации, Home/Back и безопасного изменения громкости/mute. Успех mock или HTTP не заменяет аппаратную приёмку. Непроверенные кнопки явно отмечаются в отчёте; частные данные не публикуются.
- Проходят релевантные тесты, полный `pnpm test`, `pnpm typecheck`, `pnpm build`, Chromium E2E и `git diff --check`.

Готовность этого шага не закрывает весь этап 2, этап 3 или полный MVP. Перед реализацией требуется подтверждение этой письменной спеки, затем отдельный план с задачами и способом исполнения.
