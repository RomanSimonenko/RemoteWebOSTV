# Техническое задание: Remote WebOS TV MVP

Дата: 2 сентября 2026 года
Статус: утверждено как основа MVP
Тип продукта: open-source, self-hosted

## 1. Назначение

Remote WebOS TV — self-hosted веб-приложение для управления телевизором LG на webOS из браузера. Приложение запускается на устройстве в одной локальной сети с телевизором и взаимодействует с ним через SSAP/WebSocket. Пользователь управляет телевизором через веб-интерфейс с компьютера; установка отдельного клиентского приложения не требуется.

MVP должен работать локально и допускать безопасную публикацию через внешний HTTPS-туннель или reverse proxy. Приложение не открывает порты роутера и не предоставляет собственный облачный relay.

## 2. Цели MVP

MVP подтверждает следующие продуктовые и технические гипотезы:

1. Телевизором LG на поддерживаемой версии webOS можно стабильно управлять через браузер и локальный сервер.
2. Первичное сопряжение, хранение ключа и повторное подключение работают без ручного вмешательства после однократного подтверждения на телевизоре.
3. Одно Docker-приложение достаточно для установки, эксплуатации и обновления системы.
4. Архитектуру можно позднее разделить на облачный сервис и локальный агент без изменения пользовательской модели команд.

## 3. Границы MVP

### 3.1. Входит в MVP

- запуск через Docker Compose;
- один владелец установки;
- один активный телевизор на одну установку;
- автоматический поиск телевизора и ручной ввод IP-адреса;
- первичное сопряжение с подтверждением на экране ТВ;
- сохранение и повторное использование `client-key`;
- управление из браузера;
- навигационные, системные, цифровые, цветные и мультимедийные кнопки;
- управление громкостью, каналами, приложениями и источниками сигнала;
- отправка текста в активное поле ввода телевизора;
- вывод короткого уведомления на экран ТВ;
- выключение через SSAP;
- включение через Wake-on-LAN на совместимых и настроенных моделях;
- локальный доступ по сети;
- работа за внешним HTTPS-туннелем или reverse proxy;
- встроенная авторизация владельца;
- резервное копирование и восстановление конфигурации;
- диагностика соединения и совместимости.

### 3.2. Не входит в MVP

- собственный облачный relay;
- централизованные аккаунты и многопользовательский SaaS;
- несколько владельцев, роли и приглашения;
- нативные приложения для настольных и мобильных ОС;
- передача изображения или звука с телевизора;
- скриншоты экрана ТВ;
- голосовое управление;
- гироскопический указатель Magic Remote;
- автоматическая настройка роутера;
- копирование внешнего вида конкретной модели пульта LG;
- гарантия Wake-on-LAN на моделях, которые не поддерживают удалённое включение.

## 4. Поддерживаемые устройства и платформы

Целевой диапазон — телевизоры LG с webOS 4.0 и новее. Более старые версии могут работать, но считаются экспериментальными и не входят в обязательную матрицу совместимости.

Основной физический стенд MVP — LG 43UP76906LE с отображаемой версией webOS TV 6.5.3. При первом подключении приложение получает фактические идентификаторы модели, платформы и прошивки через SSAP и использует их в отчёте совместимости вместо введённых вручную значений.

Поддержка определяется по отдельным возможностям, а не только по номеру webOS. Если телевизор сопрягается, но прошивка запрещает pointer-сокет или конкретный endpoint, приложение сохраняет доступ к остальным функциям и явно отмечает ограничение. Изменения разрешений в прошивках webOS 2026 учитываются как отдельный риск совместимости и проверяются через manifest-профили.

Официальные Docker-образы выпускаются для `linux/amd64` и `linux/arm64`. Рекомендуемые хосты — Linux-сервер, NAS, Raspberry Pi или мини-ПК в одной сети с телевизором. Запуск через Docker Desktop на macOS и Windows допускается, но автоматическое обнаружение и Wake-on-LAN могут зависеть от сетевого режима; ручной ввод IP- и MAC-адресов остаётся обязательным резервным сценарием.

Веб-интерфейс ориентирован на актуальные версии Chrome, Edge, Firefox и Safari на компьютере. Планшеты и телефоны могут использовать адаптивную версию интерфейса, но не являются основной платформой MVP.

## 5. Архитектура

MVP поставляется как одно приложение и один Docker-контейнер, но код разделяется на независимые компоненты:

```text
Браузер
   │ HTTPS / WebSocket
   ▼
Web UI
   │
   ▼
Backend API
   ├── Auth Service
   ├── TV Service
   ├── Discovery Service
   ├── Connection Manager
   └── Wake-on-LAN Service
              │
              ▼
         webOS Adapter
           ├── SSAP WebSocket
           └── Pointer Socket
              │
              ▼
          LG webOS TV

Backend API ── SQLite
```

### 5.1. Компоненты

- **Web UI** отображает мастер настройки, пульт, состояние ТВ, параметры безопасности и диагностику.
- **Backend API** является единственной точкой взаимодействия браузера с приложением, проверяет авторизацию, валидирует команды и скрывает внутренние данные телевизора.
- **Auth Service** управляет владельцем, паролем, сессиями и защитой изменяющих запросов.
- **TV Service** предоставляет прикладной интерфейс команд и состояний, не раскрывая детали SSAP вызывающим компонентам.
- **Discovery Service** выполняет локальное обнаружение и обновляет адрес телевизора.
- **Connection Manager** владеет жизненным циклом основного и pointer-соединений.
- **Wake-on-LAN Service** отвечает только за формирование и отправку magic packet.
- **webOS Adapter** инкапсулирует SSAP, регистрацию, manifest разрешений, pointer-протокол и различия прошивок.
- **SQLite** хранит владельца, сессии, конфигурацию, сведения о телевизоре и историю миграций.

Backend остаётся владельцем `client-key`: ключ не передаётся Web UI и не включается в обычные ответы API.

### 5.2. Возможность развития

Интерфейс между TV Service и webOS Adapter проектируется так, чтобы в будущей версии adapter можно было выделить в локальный агент, работающий в сети пользователя. Облачный Web UI и API будут отправлять команды агенту через исходящее защищённое соединение, не обращаясь напрямую к телевизору и не требуя открытия входящих портов дома.

## 6. Технологический стек

- язык frontend и backend: TypeScript;
- менеджер проекта: `pnpm workspace`;
- frontend: React и Vite;
- backend: Node.js и Fastify;
- обмен в реальном времени: WebSocket;
- постоянное хранилище: SQLite;
- упаковка: Docker и Docker Compose;
- модульные и интеграционные тесты: Vitest;
- браузерные тесты: Playwright в headless-режиме.

Контракты REST, WebSocket-команд и событий описываются общими TypeScript-схемами и используются для проверки данных на обеих сторонах. Конкретная библиотека работы с webOS скрывается внутри adapter и может быть заменена без изменения публичного API приложения.

### 6.1. Переиспользование готовых решений

Готовые пульты Home Assistant, браузерные демо и Windows-приложения не используются как runtime-зависимости: они либо требуют отдельную платформу, либо не обеспечивают согласованные границы авторизации и удалённого доступа.

Первичный кандидат для реализации протокольного слоя — MIT-библиотека `lgtv2`. До включения в продукт её фиксированная версия или ревизия проходит проверку на основном физическом стенде. Проверяются сопряжение, повторное подключение, WSS/WS, pointer-сокет, состояние, приложения, входы, выключение, определение MAC и Wake-on-LAN.

2026-10-01 базовый аппаратный шлюз пройден на LG 43UP76906LE с прошивкой 03.53.45: выбран `lgtv2@2.0.0` через adapter. Сохранение ключа после перезапуска процесса и ТВ, состояние, apps/inputs, pointer, кнопка HOME, уведомление и выключение через API подтверждены. Wake-on-LAN с явно заданным MAC подтверждён пользователем после ручного выключения ТВ. WS fallback остаётся непроверенным. Подробности: [отчёт совместимости](../../compatibility/lg-43up76906le-webos-6.5.3.md).

Если проверка успешна, webOS Adapter оборачивает `lgtv2` и владеет нормализацией ошибок, хранением ключей и состояниями соединения. Если критическая функция не работает, adapter использует минимальную исправленную реализацию SSAP или сопровождаемый fork; Web UI, Backend API и прикладные контракты при этом не меняются.

## 7. Авторизация

MVP использует модель одного владельца без публичной регистрации, ролей и приглашений.

### 7.1. Первичная настройка владельца

1. После первого запуска приложение остаётся в состоянии `unclaimed` и не принимает команды управления.
2. Владелец выполняет явную CLI-команду внутри контейнера для выпуска одноразового установочного токена.
3. Команда выводит токен только в текущий терминал; приложение не записывает его в журнал.
4. Владелец вводит токен в локальном Web UI и задаёт имя и пароль.
5. Backend сохраняет только криптографический хеш пароля, отзывает установочный токен и переводит приложение в состояние `claimed`.

Новый установочный токен аннулирует предыдущий, имеет ограниченный срок действия и никогда не даёт доступ к уже настроенному пульту без завершения создания владельца.

### 7.2. Сессии и защита API

- сессия передаётся через cookie с флагами `HttpOnly` и `SameSite`;
- при работе через HTTPS устанавливается флаг `Secure`;
- изменяющие REST-запросы защищаются от CSRF;
- попытки входа и сопряжения ограничиваются по частоте;
- все команды пульта требуют действующей сессии;
- настройка доверенного proxy задаётся явно и не определяется из произвольных заголовков;
- полный текст сетевых ошибок, внутренние пути и секреты не возвращаются браузеру.

Cloudflare Access или авторизация другого reverse proxy могут использоваться как дополнительный слой, но не заменяют встроенную авторизацию.

## 8. Первичное сопряжение

Сопряжение выполняет backend в локальной сети. Браузер запускает операцию и показывает её состояние, но не соединяется с телевизором напрямую.

### 8.1. Предварительные условия

- телевизор включён;
- телевизор и сервер доступны друг другу по локальной сети;
- управление мобильными устройствами разрешено в настройках ТВ;
- владелец авторизован в приложении;
- контейнер имеет сетевой доступ к телевизору.

### 8.2. Последовательность

1. Пользователь запускает поиск телевизора.
2. Discovery Service выполняет SSDP/mDNS-поиск и показывает найденные устройства. При неудаче пользователь вводит IP-адрес вручную.
3. Backend проверяет доступность устройства, пробует защищённое WebSocket-соединение на порту `3001`, затем совместимый незашифрованный вариант на порту `3000`.
4. Adapter получает базовую информацию о ТВ и выполняет предварительный запрос системной информации, если этого требует версия webOS.
5. Backend отправляет SSAP-запрос `register` с `pairingType: PROMPT`, версионируемым manifest и минимально необходимыми разрешениями.
6. Web UI показывает инструкцию подтвердить подключение на телевизоре и таймер на 60 секунд.
7. Пользователь подтверждает запрос существующим пультом на экране ТВ.
8. Телевизор возвращает ответ `registered` с `client-key`.
9. Backend проверяет ответ, сохраняет ключ, устанавливает pointer-соединение и выполняет безопасный запрос чтения состояния.
10. После успешной проверки телевизор переходит в состояние `available`, и Web UI открывает пульт.

Первичное сопряжение требует однократного физического подтверждения на экране телевизора. PIN-сопряжение, root-доступ и обход защитного запроса не используются.

### 8.3. Повторное подключение

При следующих подключениях adapter отправляет сохранённый `client-key`. Обычное выключение, отключение от розетки и перезапуск телевизора не требуют нового сопряжения. Повторное подтверждение требуется после сброса ТВ, отзыва разрешения, потери ключа или признания ключа недействительным прошивкой.

### 8.4. Ошибки сопряжения

- отказ пользователя завершает операцию без сохранения ключа;
- тайм-аут закрывает незавершённый WebSocket и разрешает явный повтор;
- потеря соединения сохраняет конкретную диагностическую причину;
- недействительный ключ переводит телевизор в состояние `authorization_error` и предлагает повторное сопряжение;
- одновременно для одного телевизора выполняется не более одной операции сопряжения;
- ключ сохраняется только после корректного ответа `registered`.

## 9. Управление телевизором

### 9.1. Команды MVP

- питание: включение и выключение;
- навигация: вверх, вниз, влево, вправо и `OK`;
- системные команды: `Home`, `Back`, `Exit` и меню;
- громкость: увеличить, уменьшить, установить значение и переключить mute;
- каналы: следующий, предыдущий и выбор номера;
- цифровые кнопки `0–9`;
- цветные кнопки;
- воспроизведение: play, pause, stop, перемотка назад и вперёд;
- получение и переключение HDMI/AV-входов;
- получение и запуск установленных приложений;
- отправка текста в активное поле ввода;
- показ короткого уведомления на экране ТВ.

Adapter определяет доступность команд по возможностям конкретной модели. Недоступная функция не эмулируется скрытым обходным способом: UI отключает её и показывает понятную причину.

### 9.2. Поток команды

1. Web UI формирует команду с уникальным идентификатором.
2. Backend проверяет сессию, схему, параметры, состояние ТВ и поддерживаемую возможность.
3. TV Service передаёт команду adapter.
4. Adapter выбирает основное SSAP-соединение или pointer-сокет.
5. Backend возвращает результат с исходным идентификатором и публикует обновлённое состояние.

Пример команды:

```json
{
  "id": "cmd_123",
  "type": "remote.command",
  "action": "volume.up",
  "parameters": {}
}
```

Если соединение разорвалось после отправки и результат неизвестен, backend не повторяет команду автоматически. Команды, поступившие во время недоступности ТВ, не ставятся в очередь и не выполняются после восстановления связи.

### 9.3. Удержание кнопок

Громкость, каналы и навигация поддерживают удержание. Web UI посылает ограниченную последовательность событий, backend применяет дополнительный лимит частоты, а отпускание или потеря фокуса немедленно прекращает повторение.

## 10. Состояния и переподключение

Backend поддерживает состояния:

- `unconfigured` — телевизор не настроен;
- `pairing` — выполняется сопряжение;
- `connecting` — устанавливается соединение;
- `available` — команды доступны;
- `unavailable` — телевизор выключен или недоступен;
- `reconnecting` — выполняется ограниченное восстановление связи;
- `authorization_error` — ключ не принят;
- `compatibility_error` — протокол или разрешение не поддерживается.

Connection Manager владеет обоими WebSocket-соединениями и закрывает их при отмене, ошибке и штатной остановке. После потери связи выполняются ограниченные попытки с увеличивающимся интервалом. Параметры ожидания и максимальный интервал конфигурируются, а их значения контролируются в тестах через внедряемые часы и генератор случайности.

После восстановления WebSocket браузер получает полный снимок состояния, затем только изменения. Доступные данные включают громкость, mute, приложение, источник, воспроизведение, канал, приложения и входы — в пределах возможностей модели.

Кнопка Wake-on-LAN остаётся доступной в состоянии `unavailable`, если сохранён MAC-адрес. После отправки magic packet backend ожидает появления ТВ и восстанавливает SSAP-соединение.

## 11. Веб-интерфейс

Основные страницы:

1. вход;
2. первоначальная настройка владельца;
3. поиск и сопряжение телевизора;
4. пульт;
5. настройки телевизора;
6. безопасность и активные сессии;
7. диагностика;
8. резервное копирование и восстановление.

Пульт MVP использует простой функциональный интерфейс без реалистичной визуализации физического устройства. Команды собраны в понятные группы: навигация, системные действия, громкость и каналы, цифры, воспроизведение, приложения и входы.

Требования к интерфейсу:

- управление мышью и клавиатурой;
- стрелки выполняют навигацию, `Enter` — `OK`, `Escape` — `Back`;
- горячие клавиши отключаются при вводе текста;
- нажатие получает немедленную визуальную обратную связь;
- фактический результат команды отображается отдельно от локального состояния кнопки;
- недоступные команды блокируются с объяснением;
- состояние соединения видно постоянно;
- интерфейс не требует перезагрузки после команд или переподключения;
- состояние элементов не передаётся только цветом;
- опасные действия требуют явного подтверждения;
- масштабирование браузера не скрывает основные команды.

## 12. Удалённый доступ

В локальной сети приложение доступно напрямую. Для доступа из интернета пользователь подключает внешний HTTPS-туннель или reverse proxy с поддержкой WebSocket.

Cloudflare Tunnel документируется как рекомендуемый вариант MVP, но не является обязательной зависимостью приложения. Допускаются другие reverse proxy и туннели, если они обеспечивают HTTPS, передачу WebSocket и корректную передачу доверенных заголовков.

Прямое открытие HTTP-порта приложения в интернет не поддерживается. Приложение не меняет настройки роутера, не выпускает домены и не управляет аккаунтом внешнего провайдера.

## 13. Данные, секреты и резервные копии

SQLite хранит:

- владельца и хеш пароля;
- серверные сессии;
- название, модель и возможности телевизора;
- последний известный IP-адрес;
- MAC-адрес;
- выбранный транспорт и порт;
- зашифрованный `client-key`;
- дату последнего успешного соединения;
- версию схемы данных.

Мастер-ключ приложения создаётся на первом запуске, хранится отдельно от SQLite в постоянном volume и имеет минимальные файловые разрешения. Компрометация всего volume считается компрометацией установки; приложение не заявляет защиту от владельца или администратора хоста.

Резервная копия конфигурации экспортируется только в зашифрованном виде. Ключ шифрования выводится из введённой пользователем парольной фразы с помощью устойчивой функции формирования ключа, а содержимое защищается аутентифицированным шифрованием. Парольная фраза не сохраняется.

Восстановление проверяет формат, версию, целостность и пароль до изменения текущих данных. Перед заменой создаётся локальная восстановительная копия. Операция требует повторного подтверждения владельца и не выполняется частично.

Диагностический экспорт скрывает ключи, cookie, хеши паролей, токены, внутренние пути и другие чувствительные значения.

## 14. Развёртывание и обновление

Поставка включает:

- Dockerfile и опубликованный образ;
- `compose.yaml`;
- пример несекретной конфигурации;
- постоянный volume;
- проверку работоспособности контейнера;
- инструкции локального запуска и настройки удалённого HTTPS-доступа.

Контейнеру требуется доступ к локальной сети для SSAP, SSDP/mDNS и Wake-on-LAN. Порт Web UI задаётся конфигурацией. Адреса телевизора, домены, пути хоста и секреты не встраиваются в исходный код.

Обновление выполняется заменой образа. Перед миграцией SQLite создаётся восстановительная копия. Миграции выполняются транзакционно и последовательно. Ошибка миграции оставляет предыдущие данные доступными для отката, завершает запуск с ненулевым кодом и сохраняет конкретную причину в редактированном от секретов серверном журнале.

Проверка работоспособности оценивает backend и хранилище. Выключенный телевизор не переводит контейнер в состояние `unhealthy`.

## 15. Ошибки и диагностика

Ошибки классифицируются по владельцу проблемы:

- сеть и недоступность ТВ;
- сопряжение и авторизация ТВ;
- несовместимая возможность;
- авторизация пользователя;
- валидация команды;
- хранилище и миграции;
- туннель или proxy;
- внутренняя ошибка приложения.

Web UI получает безопасный код, понятное сообщение и идентификатор операции. Серверный журнал сохраняет причинную цепочку и тот же идентификатор, но редактирует секреты и персональные данные. Ошибки не подавляются и не заменяются успешным ответом.

Страница диагностики показывает состояние соединений, модель и версию webOS, доступные возможности, последнее успешное подключение и безопасные сведения о последних ошибках.

## 16. Тестирование

### 16.1. Модульные тесты

Покрывают:

- формирование и разбор SSAP-сообщений;
- валидацию команд и событий;
- переходы состояний Connection Manager;
- отсутствие повторной отправки при неопределённом результате;
- ограничение удерживаемых кнопок;
- авторизацию и ограничения частоты;
- миграции SQLite;
- шифрование и восстановление резервных копий;
- удаление секретов из ошибок и диагностики.

### 16.2. Интеграционные тесты

Создаётся детерминированный эмулятор webOS TV с основным и pointer-WebSocket. Он воспроизводит:

- успешное сопряжение;
- отклонение запроса;
- тайм-аут;
- недействительный ключ;
- отсутствие требуемого разрешения;
- разрыв до и после отправки команды;
- изменение IP;
- включение и выключение;
- подписки на состояние.

Тесты времени и переподключения используют управляемые часы и сигналы, а не реальные задержки.

### 16.3. Браузерные тесты

Playwright в headless-режиме проверяет вход, первичную настройку, сопряжение, команды пульта, отображение ошибок, переподключение, резервное копирование и восстановление.

### 16.4. Реальный телевизор

Первый обязательный стенд — LG 43UP76906LE с webOS TV 6.5.3. До реализации остального продукта на нём проводится протокольная проверка выбранной версии `lgtv2`. Перед выпуском MVP выполняется полный повторный прогон. Результат фиксируется в таблице совместимости: фактическая модель, версия платформы и прошивки, транспорт, сопряжение, повторное подключение, pointer-сокет, Wake-on-LAN и отдельные команды.

## 17. Критерии приёмки MVP

MVP считается готовым, когда свежая проверка подтверждает все условия:

1. Приложение запускается через Docker Compose и сохраняет данные в volume.
2. Владелец безопасно создаёт учётную запись и входит в систему.
3. Неавторизованный пользователь не может читать конфигурацию или выполнять команды.
4. Телевизор находится автоматически либо добавляется по IP.
5. Первичное сопряжение завершается после подтверждения на ТВ.
6. Повторное подключение не запрашивает подтверждение после перезапуска приложения и телевизора.
7. Согласованный набор кнопок управляет поддерживаемыми функциями реального ТВ.
8. Приложения и входы загружаются и переключаются.
9. Недоступный телевизор не нарушает работу Web UI и backend.
10. После появления ТВ соединение восстанавливается без выполнения устаревших команд.
11. Wake-on-LAN работает на совместимой и предварительно настроенной модели.
12. Удалённое управление работает через внешний HTTPS-туннель с WebSocket.
13. Секреты отсутствуют в Web UI, API, обычных журналах и диагностическом экспорте.
14. Зашифрованная резервная копия восстанавливает конфигурацию и сопряжение, если телевизор принимает сохранённый ключ.
15. Автоматические тесты проходят в CI, а ручной результат внесён в таблицу совместимости.

## 18. Принципы дальнейшего развития

После подтверждения MVP система может развиваться в полноценный сервис:

- webOS Adapter выделяется в локальный агент;
- агент устанавливает только исходящее защищённое соединение;
- Web UI и публичный API переносятся в облако;
- добавляются аккаунты, несколько домов и телевизоров;
- команды и события сохраняют совместимый прикладной контракт;
- `client-key` остаётся на локальном агенте и не передаётся облаку.

Эти возможности не должны усложнять пользовательский интерфейс или развёртывание MVP до появления подтверждённой рабочей версии.
